# 人事簽核流程開發規範

本規範適用於依單位主管逐級簽核的案件。班表、臨時調班與請假可共用同一套規則。全院統一審核的個資與證照異動可以使用共用的簽核服務，其審核路徑由全院流程另行定義。

各模組的需求、適用權限及驗收範圍見 [人力資源系統開發需求規範](development-requirements.md)。

目前的流程圖是依現有組織資料與已確認規則推算的設計。現有 `hr` schema 提供組織與主管資料，正式的案件簽核功能與流程設定尚未實作。

## 資料與程式的分工

| 內容 | 來源或保存位置 |
|---|---|
| 員工的所屬單位 | `hr.employee.department_id` |
| 單位的上層及啟用狀態 | `hr.department.parent_id`、`is_active`。院級為 `department_id = 1` |
| 主管身分與任期 | `hr.department_manager` 的單位、員工、角色及任期。正主管與代理主管同時間合計最多一筆有效指派，職稱用於顯示 |
| 院級要簽核或知會 | 規劃由具流程設定權的使用者維護，按單位與申請類型套用。相同流程可共用設定。正式儲存結構另行確認 |
| 上溯、跳過本人、強制院級簽核 | 共用的後端簽核服務依本規範判定 |
| 案件實際使用的關卡及處理結果 | 正式流程實作時保存每筆案件實際採用的路徑、簽核人與動作，以及其執行結果 |

組織、主管及使用者設定是程式的輸入。簽核服務應以這些資料產生路徑，避免在程式中逐一寫死單位、人名或員工編號。院級動作也不需要在部門表、主管表和流程設定各存一份。

## 路徑判定

1. **確認發起單位。** 員工本人申請應依案件適用的所屬單位起算。單位班表等業務案件應以該案件的責任單位起算。發起人及其權限由後端確認。
2. **區分入口及上溯節點。** 沒有直接編列在職員工的單位，不單獨列為一般員工的發起單位。例如內外科與復健科。子單位的案件仍沿 `parent_id` 經過這些單位。若其中有具簽核權的正主管或代理主管，該層仍須納入簽核。
3. **從發起單位逐級往院級查找。** 每一層使用當時唯一有效的正主管或代理主管。沒有主管就繼續上溯，找到下層主管後仍須檢查其上層，直到院級為止。正主管與代理主管交接時，兩者有效期間不得重疊。路徑循環、斷層或同層出現多筆有效指派時，列為待處理。
4. **主管本人在院級以下發起時，略過他本人的簽核關卡。** 若同一人在不同層級兼任，每一個由本人簽核的下層關卡都要略過。其他人的有效關卡依原順序處理。
5. **合併同一人兼任的簽核關卡。** 若簽核人並非發起人，以 `employee_id` 識別，同一案件只簽一次，並保留該次簽核所涵蓋的所有層級。下層重複關卡保留該人首次出現的位置。合併涉及院級簽核時，保留院級簽核在最後，使其在其他簽核之後執行。院級知會仍依設定送出。
6. **每條流程都要到院級。** 在排除不適用的下層關卡後，若仍有下層簽核，院級依使用者設定採簽核或知會。若下層已無可執行的簽核關卡，院級必須簽核。這也適用於原設定為知會，但略過發起主管後已無下層簽核人的案件。下層關卡尚待分派、待簽或已退回，不能視為下層無人可簽。
7. **院級主管以院級身分發起時，由本人簽核。** 院級已是最高層，仍須留下本人執行簽核的紀錄。

跨單位調班沿用原本的簽核順序，跨單位本身不增減或重排關卡。若涉及交換班次，原有的換班對象先確認規則照常適用。

## 簽核、知會與案件生效

- **簽核**須取得該關核准才能往下走。所有必要簽核完成後，案件才依其業務規則生效。
- **知會**在前面的必要簽核完成後送到院級。案件不需要等院級同意才生效。通知的送達與重試可另外追蹤。
- 有下層簽核且院級動作沒有設定時，須明確呈現為待設定，不能把未設定當成知會。
- 案件送出時保存實際適用的關卡與院級動作。之後組織或流程設定有變更時，不能在背景改寫既有案件。
- 院級無人承接，或案件送出後需要改派時，先通知系統管理者並保存待處理的原因。本階段只通知，不自動改派、跳過必要關卡或代為核准。必要簽核無人承接時，案件維持待處理。院級只有知會時，收件異常列為通知待處理，案件仍依必要簽核的結果生效。
- LINE 與一般瀏覽器共用同一套後端判定及同一筆案件。後端須核對操作者是否有權執行該關，並確保同一關從兩個入口送出時只會生效一次。

## 驗收案例

測試可使用合成員工與部門資料。以下以實際組織名稱說明已確認的路徑，正式環境的人選依主管指派取得。

| 案件 | 預期路徑或結果 |
|---|---|
| 保險申報組一般員工發起，院級設定為知會 | 保險申報組組長簽核 → 管理部課長簽核 → 院級副院長知會 |
| 復健科／小兒組發起，院級設定為簽核 | 小兒組主管簽核 → 復健科代理主管簽核 → 院級副院長簽核。復健科雖無直屬員工，仍有簽核關卡 |
| 外科組發起，沿途沒有院以下簽核人 | 直接由院級副院長簽核 |
| 管理部課長本人發起 | 略過課長本人，由院級副院長簽核。即使原流程設定院級知會，這筆仍須院級簽核 |
| 院級副院長本人以院級身分發起 | 由本人在院級完成簽核 |
| 同一單位已有有效的正主管，再新增重疊任期的代理主管 | 不允許同時生效。代理接任須與正主管的有效期間錯開 |
| 病房組與護理部由同一人兼任，該人並非發起人 | 只須簽一次，簽核紀錄涵蓋兩層，院級依原設定繼續處理 |
| 調班涉及兩個單位 | 簽核沿用原本的關卡順序，跨單位本身不新增關卡 |
| 院級找不到處理人，或送件後需要改派 | 通知系統管理者並顯示待處理原因，現有路徑與未完成的必要簽核均保留 |
| 內外科無直屬員工 | 發起單位列表不顯示內外科。病房組案件仍照其組織階層往上找簽核人 |
| 下層已有簽核人，但院級動作未設定 | 顯示待設定。下層有人簽核並不推導出院級知會 |

## 主管指派的資料庫限制

本機與 Supabase 共用 [主管唯一索引](../database/migrations/20261120073928_restore_exclusive_current_department_supervisor.sql)。每個單位在 `role IN ('head', 'acting')` 且 `end_date IS NULL` 的資料中最多一筆。若登錄指定起迄日的任期，寫入時還須檢查有效期間重疊。
